# Gradely — Backend

Node.js + TypeScript + Express API for Gradely, talking directly to Neon
PostgreSQL through the `pg` driver, deployed as a Vercel Function.

> **Status:** Phase B (school management). Phase A’s email-verification
> foundation remains in place. School administrators can now manage a school
> profile and logo, classes (one per level across the 14-level progression),
> sections, subjects, and class-subject assignments. Platform administrators
> have read-only oversight. Teacher invitations, pupils, assessment entry,
> report generation, and payments belong to later phases.

## Stack

- Node.js 24 (ESM), TypeScript, Express 5
- Neon PostgreSQL via `pg` (node-postgres) with a lazy shared pool
- Cloudflare R2 via `@aws-sdk/client-s3` (S3-compatible)
- Zod for environment validation
- Helmet + environment-driven CORS
- ESLint 10 + typescript-eslint, Vitest + Supertest

## Deploying to Vercel (backend project)

Import the same Git repository as a **second** Vercel project with:

- **Root Directory:** `backend`
- **Framework Preset:** Express (auto-detected; also set in `vercel.json`)
- **Node.js version:** 24.x (pinned via `engines` in `package.json`)

Vercel detects `src/app.ts`, which default-exports the Express app, and
serves it as a single Vercel Function. `vercel.json` sets
`buildCommand: npm run build` (TypeScript compile — no database, no
credentials, and no external code generation required).

Set the environment variables below in the Vercel project (Production,
Preview, Development as appropriate). Never commit real credentials.

## Environment variables (backend Vercel project)

| Variable | Required | Purpose |
| --- | --- | --- |
| `CORS_ORIGINS` | Yes (prod) | Comma-separated allowed frontend origins, e.g. `https://your-frontend.vercel.app` |
| `DATABASE_URL` | Yes (when DB features ship) | **Neon pooled** connection string (`-pooler` host) used by the runtime `pg` pool |
| `DIRECT_URL` | For migrations | **Neon direct** connection string (no `-pooler`) used by `npm run db:migrate`; falls back to `DATABASE_URL` |
| `NODE_ENV` | Optional | Set by Vercel to `production`; defaults to `development` locally |
| `PORT` | No | Local dev only; ignored on Vercel |
| `R2_ACCOUNT_ID` | For storage | Cloudflare account ID |
| `R2_ACCESS_KEY_ID` | For storage | R2 API token access key (Object Read & Write on one bucket) |
| `R2_SECRET_ACCESS_KEY` | For storage | R2 API token secret key |
| `R2_BUCKET_NAME` | For storage | R2 bucket name (e.g. `gradely-files`) |
| `R2_PUBLIC_BASE_URL` | No | Optional public base URL for non-private assets only |
| `BOOTSTRAP_ADMIN_PASSWORD` | Bootstrap only | One-off password used by `npm run admin:create` (never set it in Vercel) |
| `EMAIL_TRANSPORT` | Optional | Verification email transport: `log` (development), `memory` (tests), or `unavailable` (production default). No vendor adapter is configured yet. |
| `GRADELY_ENV` | Local scratch only | `scratch` enables strict local-target validation. Defaults to `development`; do not set it in Vercel. |
| `GRADELY_ENV_FILE` | Local scratch only | Explicit environment file selected instead of `.env`. Required for scratch commands. |
| `SCRATCH_DATABASE_URL` | Local scratch only | Dedicated loopback scratch target used by `--scratch` migrations/admin commands and local startup. |
| `MIGRATION_DATABASE_URL` | Local scratch only | Optional explicit migration target. Normal mode still falls back to `DIRECT_URL`, then `DATABASE_URL`. |
| `TEST_DATABASE_URL` | Tests only | Scratch PostgreSQL URL for `npm run test:db` and `npm test`. Must be loopback (`127.0.0.1`/`::1`), use `gradely_scratch` or `gradely_test_*`, and connect as a non-superuser role. Missing or unsafe values fail closed. |

Scratch-only variables belong in a separate, gitignored file outside the
repository. They must never be added to `backend/.env` or to Vercel.

No new variables are required for authentication itself: sessions are
server-side (PostgreSQL) and the session cookie is generated by the API.
`CORS_ORIGINS` must list the deployed frontend origin(s) — CORS now runs
with `credentials: true` so the browser can send the session cookie.

The API and `GET /api/health` start **without** database or R2 credentials.

## Local development

```bash
npm install               # install dependencies
copy .env.example .env    # then edit values (placeholders only in the example)
npm run dev               # API on http://localhost:4000
```

`.env` is gitignored. Never commit real credentials. A local PostgreSQL
server is **not** required to start the API or pass the health check.

If your local `.env` contains production Neon values, do not run scratch
commands from `backend/` without selecting a scratch-only file:

```powershell
$env:GRADELY_ENV = 'scratch'
$env:GRADELY_ENV_FILE = "$env:APPDATA\Gradely\scratch.env"
npm run dev
```

In scratch mode the loader refuses to fall back to `.env`. The selected file
must use a loopback host and an exact scratch database name such as
`gradely_scratch`.

## Commands

```bash
npm run dev             # start API with hot reload (tsx watch) on :4000
npm run build           # compile TypeScript to dist/ (local production run)
npm start               # run the compiled API (requires npm run build)
npm run lint            # ESLint
npm run typecheck       # TypeScript check (no emit)
npm run test:unit       # database-free tests; no scratch DB required
npm run test:db         # database integration tests; fails closed without a safe TEST_DATABASE_URL
npm test                # full suite; also fails closed without a safe TEST_DATABASE_URL
npm run db:migrate      # apply pending SQL migrations (normal mode; remote targets need --allow-remote)
npm run db:migrate:status # list applied/pending migrations (read-only)
npm run admin:create    # bootstrap/grant the platform administrator account
```

### Database safety authorization

These are separate approvals, not one combined authorization:

- creating a local scratch role/database;
- running migrations against any database;
- running destructive database integration tests;
- any production migration, admin bootstrap, deployment, or R2 operation.

`npm run test:unit` is the only test command that is database-free. `npm test`
and `npm run test:db` require a valid `TEST_DATABASE_URL` and fail closed
without one.

## Authentication & authorization

Design (deliberately small, no auth framework, no JWT):

- **Passwords** — Node's built-in `scrypt` (OWASP parameters: N=2^17, r=8,
  p=1, 64-byte key) in `src/lib/passwords.ts`. Stored as self-describing
  `scrypt$...` hashes; verification is constant-time and never throws on
  malformed input. Unknown emails burn equivalent scrypt work
  (`verifyPasswordDummy`) so login timing cannot enumerate accounts.
- **Sessions** — opaque 256-bit tokens (HttpOnly, SameSite=Lax,
  Secure-in-production cookie, 7-day expiry) backed by the `sessions`
  table. Only SHA-256 hashes are stored; logout revokes server-side, so a
  stolen database row cannot be replayed and a logged-out cookie is dead.
  JWT was rejected precisely because it cannot be revoked instantly.
- **Login endpoint** — `POST /api/auth/login` validates with Zod, applies
  per-IP+email rate limiting (10 failures / 15 min, in-memory;
  per-instance under serverless — documented trade-off), returns the same
  401 for unknown email and wrong password, and reveals "account disabled"
  only after a correct password. State-changing auth endpoints also enforce
  the `Origin` header against the CORS allow-list (login-CSRF guard).
- **Authorization** — `src/middleware/auth.ts`. `requireAuth` loads the
  session; `requirePlatformAdmin` is explicit platform-level power (never a
  membership shortcut); `authorizeSchoolAccess()` resolves school access
  **only** from the user's active membership **and** an `active` school —
  a school ID in a request is just a lookup key. Suspended/archived schools
  are denied even to members whose membership row is still active.
  Platform administrators may still read those schools through the explicit
  `allowPlatformAdmin` path (oversight), never through a membership. Missing
  schools and unauthorized schools both return an identical 404 so IDs
  cannot be enumerated.
- **Bootstrap** — public self-service registration creates a *school
  administrator* only (`POST /api/auth/register-school`); it can never grant
  platform-admin rights. The first platform administrator is still created
  by an operator with database access via `npm run admin:create` (password
  read from `BOOTSTRAP_ADMIN_PASSWORD`, stored only as a scrypt hash).
  Teacher invitations are a later phase.
- **Email verification (Phase A)** — registration creates
  `schools.status = 'pending_verification'` and the founding membership as
  `pending` in one transaction, then emails a single-use link. Only the
  SHA-256 hash of the token is stored (`email_verification_tokens`); tokens
  expire after 24 hours and are consumed atomically. Redemption marks
  `users.email_verified_at`, flips the founding membership `pending ->
  active`, and flips the school `pending_verification -> active`. Suspended
  or archived schools are never reactivated. Resends supersede earlier
  tokens (at most one live token per user, enforced by a partial unique
  index plus a per-user advisory lock). Until verification,
  `requireVerifiedEmail` returns `403 email_verification_required` for
  school features while `/api/auth/me` stays available for the resend UI.
  Login remains possible for unverified accounts (no account-detail leak)
  so the user can reach the verification screen.
- **Email transport** — `EmailService` is provider-independent
  (`src/services/email.ts`). Development logs the message, tests use an
  in-memory outbox, and production defaults to `unavailable` (delivery fails
  loudly) until a real vendor adapter is approved. Request/error handlers
  never log raw tokens, and production logs never include the body. The
  development-only `log` transport prints the message body (including the
  clickable link) to the local console so developers can complete the flow;
  `EMAIL_TRANSPORT` must never be `log` in production.

API surface added this phase:

```
POST /api/auth/login              # email + password → session cookie
POST /api/auth/logout             # revoke session + clear cookie
GET  /api/auth/me                 # current user + active memberships
POST /api/auth/register-school    # school + admin transaction, email link
POST /api/auth/verify-email       # redeem single-use verification token
POST /api/auth/resend-verification# uniform 202, rate limited, supersedes
GET  /api/schools/mine            # caller's active memberships
GET  /api/schools/:id             # school details for members (or platform admin)
```

Phase B school-management API (all require a verified session; writes also
require the trusted `Origin` header):

```
GET   /api/schools/:id/overview                    # profile + setup checklist/counts
GET   /api/schools/:id/class-levels                # the 14 levels, stable order
GET   /api/schools/:id/classes                     # classes with sections/counts
GET   /api/schools/:id/classes/:classId            # class detail + assignments
GET   /api/schools/:id/subjects                    # subjects with assignment counts
PATCH /api/schools/:id/profile                     # name/contact fields (slug immutable)
POST  /api/schools/:id/classes                     # one class per level
PATCH /api/schools/:id/classes/:classId            # archive/reactivate class
POST  /api/schools/:id/classes/:classId/sections   # add section
PATCH /api/schools/:id/classes/:classId/sections/:sectionId
POST  /api/schools/:id/subjects                    # add subject
PATCH /api/schools/:id/subjects/:subjectId         # rename/archive/reactivate
POST  /api/schools/:id/classes/:classId/subjects   # assign subject
PATCH /api/schools/:id/classes/:classId/subjects/:subjectId
GET   /api/schools/:id/logo                        # fresh short-lived preview URL
POST  /api/schools/:id/logo/uploads                # presign one direct R2 PUT
POST  /api/schools/:id/logo                        # HEAD-verify, then persist
DELETE /api/schools/:id/logo                       # clear reference + best-effort delete
```

Authorization: school administrators can write to their own school only;
teachers receive `403`; platform administrators can read overview/classes/
sections/subjects (including suspended/archived schools) but every write
returns a non-leaking `404`. Child lookups are scoped by both school and
parent IDs, so a missing row and another school's row are indistinguishable.
Archiving is soft (`status = 'archived'`); no management endpoint hard-deletes
school data. Logo object keys are internal and are never returned by the API.

Class levels are seeded in `0004_school_management.sql` in the required order:
Creche, Nursery 1, Nursery 2, KG 1, KG 2, Basic 1–6, JHS 1–3. Ordering uses
the explicit `sort_order` column, not labels.

## Health endpoints

```
GET /api/health      # liveness — never touches the database
GET /api/health/db   # database check — read-only SELECT 1
```

`GET /api/health` returns `200` with service status, environment, and
uptime. It deliberately does **not** touch the database or R2, so the API
starts and answers health checks without external services.

`GET /api/health/db` runs a read-only `SELECT 1` with a short timeout and
returns `200 {status:"ok", database:"up"}` or a safe
`503 {status:"unavailable", database:"down"}` — never error details or
connection strings. Access is lazy: `getDbPool()` (`src/lib/db.ts`) and
`getR2Client()` (`src/lib/r2.ts`) create their clients on first use only.

## Database (Neon PostgreSQL + pg)

- Runtime queries use a **lazy shared `pg` pool** (`src/lib/db.ts`):
  created on first use from the **pooled** Neon connection (`DATABASE_URL`,
  `-pooler` host), one pool per warm serverless instance — never a new pool
  per request.
- SSL/TLS: Neon requires encryption; `sslmode=require` stays in the
  connection string and `pg` parses it (treated as full certificate
  verification in pg 8.23).
- Migrations are plain SQL files in `backend/migrations/`, applied by
  `npm run db:migrate` (`src/scripts/migrate.ts`). Normal mode uses
  `MIGRATION_DATABASE_URL`, then the **direct** Neon endpoint
  (`DIRECT_URL`), then `DATABASE_URL`; any non-loopback target requires the
  explicit `--allow-remote` confirmation flag. Scratch mode
  (`--scratch`/`GRADELY_ENV=scratch`) requires `SCRATCH_DATABASE_URL` and
  validates the target and connected role before writing. Applied versions
  are tracked in `schema_migrations`.
- In scratch mode, the migration/admin entry points load only an explicit
  `GRADELY_ENV_FILE`; they never fall back to `.env`.
- Database integration tests use `TEST_DATABASE_URL` only. They require
  `NODE_ENV=test`, a loopback host, an exact scratch database name, and a
  non-superuser role. Missing or unsafe configuration fails closed. The
  public schema is dropped and recreated only after the connected database
  and role have been verified.
- Application queries live in `src/services/auth.ts` (users, sessions,
  memberships, verification tokens) and `src/services/schools.ts` (profile,
  classes, sections, subjects, assignments, logo references) through the
  shared pool.
  `0001_auth_foundation.sql` creates the auth tables,
  `0002_email_verification.sql` adds `users.email_verified_at` and
  `email_verification_tokens`, `0003_school_verification_lifecycle.sql`
  adds the pending school/membership states plus the one-live-token index,
  and `0004_school_management.sql` adds the profile fields, the 14-row
  `class_levels` catalogue, and the composite school-scoped tables
  (`school_classes`, `class_sections`, `subjects`, `class_subjects`).
  All four are intended to be applied to a disposable scratch PostgreSQL
  database first; they have **not** been applied to production in this phase.
  **Do not run migrations without approval.**

Phase B integrity rules live in the database as well as the service layer:

- one `school_classes` row per `(school_id, class_level_code)`;
- child tables use composite `(id, school_id)` foreign keys, so a section or
  assignment can never point at another school's parent even if application
  authorization is bypassed;
- case-insensitive unique names for sections within a class and subjects
  within a school;
- a school's `logo_key` must live under that school's own
  `school-logos/{schoolId}/` prefix, and logo key/content-type/timestamp must
  be either all set or all null.

## Cloudflare R2 (file storage)

`src/lib/r2.ts` prepares S3-compatible access for school logos, pupil
photographs, generated report PDFs, and other school documents:

- Credentials stay in backend environment variables (never sent to the
  browser; the frontend never receives storage credentials).
- Objects are private by default; clients get short-lived presigned URLs
  generated server-side (default 5 minutes).
- Generic uploads must pass `assertValidUpload()` (MIME allow-list, 10 MB
  size cap); keys are namespaced per school via `buildObjectKey()`.
- School logos use a stricter path: PNG/JPEG/WebP only, 2 MB maximum, and
  keys of the form `school-logos/{schoolId}/{uploadId}.{ext}`. The browser
  uploads directly with a short-lived presigned `PUT`, then the API performs
  a server-side `HEAD` to verify content type, size, and existence before
  persisting the reference. Replacing or removing a logo updates the database
  first and deletes the previous object on a best-effort basis.
- Files are never written to the function's local disk (it does not persist
  across serverless invocations).
- R2 upload and bucket CORS behavior have **not** been independently verified
  in this phase. The configured bucket name is not unambiguously
  non-production, so the real upload/CORS test is reported as blocked rather
  than run against an uncertain target. The upload lifecycle is covered by
  HTTP tests with an injected fake storage implementation; the
  `logo_storage_unavailable` response keeps the rest of the profile usable
  when R2 is not configured.

## Architecture notes (serverless)

- `src/app.ts` default-exports the Express app (Vercel zero-config
  detection); `src/index.ts` is the local `app.listen` entry.
- No persistent local disk or in-memory state is used for durable data —
  PostgreSQL and R2 are the durable stores.
- Errors return JSON without stack traces; 5xx details are only logged
  server-side.
